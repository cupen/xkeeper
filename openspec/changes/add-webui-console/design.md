# Design — add-webui-console

## Context

后端骨架已就绪：共享状态投影（`server.rs` 的 `ProgramInfo`/`StatusDoc`）、
`/api/*` REST、`/ws` 二进制推送（快照 → 500ms 状态 diff → 日志帧 → 心跳）、
逐泵线程 + 环形缓冲 + 落盘轮转（`pump.rs`）。缺口三块：

1. 前端是占位页，`webui-ui` 规范的整套界面未实现；
2. 无任何资源指标采集（CPU/内存），投影无字段可显示；
3. 日志推送路径逐行处理——pump 逐行 `ring.push`（每次加锁、逐订阅者克隆）、
   逐行 `write_all` + `seek`（每行 3 次系统调用）、WS 逐行发帧（每行一次
   通道 send）。10MB/s ≈ 5 万行/秒时，锁竞争、分配与系统调用都会先于网络
   成为瓶颈。

约束：项目极简依赖风格（手写控制面 HTTP、砍过 TLS 栈）；`/v1`、`/api`、
WS 三处同源修改；平台差异需 Linux/Windows 双路径覆盖。

## Goals / Non-Goals

**Goals:**

- **零干扰（先决）**：一切新增路径对受管 app 进程的影响为零——不反压
  输出、不触碰进程、不加无界开销、故障互相隔离（详见 D6）。
- 落地完整控制台 UI（既有 `webui-ui` 规范）+ 指标展示 + 高吞吐日志。
- 指标采集为守护进程级能力（`run` 与 `webui` 都采集），经共享投影三处
  同源暴露。
- 高速日志（10MB/s 量级）下：落盘与环形缓冲始终完整、无损；实时流尽力
  而为，跟不上时显式丢行标记；后端与浏览器内存均有界。

**Non-Goals:**

- 不做历史指标存储/时序数据库（只保留最近 300s 的速率窗口与当前瞬时值）。
- 不做日志内容采样/过滤模式（如"每 N 行取一行"的降采样开关）——丢行
  标记 + 速率指示已够，留作未来选项。
- 不改 CLI `log`/`status` 的输出格式（新字段只在 JSON API/投影层）。
- 不做虚拟滚动等重型前端优化；有界缓冲 + 批量渲染先行，不够再上。

## Decisions

### D1. 指标采样：独立 1Hz 线程 + 自有表，不进守护循环

`metrics.rs` 起一个常驻采样线程（守护进程启动即运行）：每秒从共享状态
读出 (程序名 → pid) 列表（只读、短暂持锁），对每个 pid 采样 CPU 时间与
RSS，与上一秒基线求差得 `cpu_percent`；同时采系统级指标。结果写入独立的
`Mutex<MetricsTable>`（或 arc-swap），投影函数按 (app, name) 合并输出。

- 为什么不放进守护循环：守护循环是 7 态状态机唯一写者，采样是纯只读
  旁路，塞进去会拉长循环周期、混淆写者边界。
- 为什么不写进 `ManagedProgram`：避免采样线程每秒写 supervisor 状态锁；
  独立表读写路径更短，投影时合并即可。
- pid 消失（退出竞态）→ 删除基线、指标置 null；新 pid → 重建基线，首次
  采样只有基线没有差值，该秒 cpu_percent 为 null（规范已定义此语义）。

**平台路径**（无新跨平台依赖）：

| 指标 | Linux | Windows |
|---|---|---|
| 进程 CPU | `/proc/<pid>/stat` utime+stime（tick，CLK_TCK） | `GetProcessTimes` |
| 进程 RSS | `/proc/<pid>/statm` rss × page_size | `GetProcessMemoryInfo` |
| 系统 CPU | `/proc/stat` 聚合行差值 | `GetSystemTimes` |
| 系统内存 | `/proc/meminfo` MemTotal/MemAvailable | `GlobalMemoryStatusEx` |

CPU% 按逻辑核心数归一（100 = 占满整机），与系统概况同口径，列表条形图
可比。`/proc/<pid>/stat` 的 comm 字段可含空格/括号，从最后一个 `)` 向后
解析。Windows 需要 `windows-sys` 增补 feature（SystemInformation / PSAPI
一族），仅 feature 增补不加 crate；进程句柄只请求
`PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ`（纯查询权限，
无挂起/终止/写入能力），采样器与守护循环无共享锁的跨系统调用持锁。

### D2. 日志速率：泵热路径上仅一次原子自增，1Hz 线程转桶

每流一个 `RateCounter`：热路径上 pump 每行只做 `total.fetch_add(1,
Relaxed)`（5 万行/秒下可忽略）；采样线程每秒把当秒计数转入最近 300 格的
滚动桶（`VecDeque<u64>`，小锁）。投影时按窗口（1/10/60/300s）求和平均。
计数器挂在 `Ring` 上（随流生命周期，重启时在 spawn 路径清零）。

- 备选：在环形缓冲 push 处计数——多一次锁；在 WS 订阅处计数——违反
  "无查看者仍计数"。泵线程是唯一过手每一行且无锁的位置。

### D3. 投影扩展：字段内嵌 `ProgramInfo`/`DaemonInfo`，三处自动同源

```
ProgramInfo += cpu_percent: Option<f64>
             += mem_bytes:   Option<u64>
             += log_rate:    { out: {w1,w10,w60,w300}, err: {...} }   // 行/秒
DaemonInfo  += system: { cpu_percent, mem_used_bytes, mem_total_bytes }
```

serde 增量字段（Option + 新子结构），JSON/MessagePack 双编码自动同构，
`/v1`、`/api`、WS 快照与增量零额外代码同步。WS 状态 diff 仍是 500ms 一轮：
指标每秒变 → 每秒一次小增量帧，规模可忽略（10 程序 ≈ 数百字节）。

**刷新频率语义**（用户需求"默认 3s，可调 1/3/5/10s"落到前端）：后端采样
固定 1Hz、推送随 diff 节奏；1/3/5/10s 只是浏览器显示节流（localStorage
持久化），日志跟随流不受节流。备选"客户端下发期望频率"被否：加协议状态
而无带宽收益。

### D4. 高吞吐日志管道：全线批量化 + 有界队列 + 丢行标记

```
child pipe
   │  (pump 线程)
   ▼
┌─────────────────────────────────────────────────────┐
│ 行级: rate_total.fetch_add(1)                        │
│ 攒批: 本地 String 缓冲, ≥256KiB 或 ≥50ms 触发 flush   │
└───────────────┬─────────────────────────────────────┘
                │ 一次 flush = 1 次文件 write + 1 次
                │ ring.push_batch + 每订阅者 1 次批量投递
                ▼
   ┌────────────┐     有界批量通道        ┌─────────────┐
   │ ring (无界) │ ─────────────────────> │ WS 订阅任务  │
   │ + 落盘文件  │  sync_channel(K 批)     │ drain→攒帧   │
   └────────────┘                         └──────┬──────┘
      永远完整、无损                            │ ≥64KiB 或 ≥100ms
      （真实之源）                              ▼ 一帧多行
                                          out_tx(有界) → ws sink → 浏览器
                                                                       │
                                              有界行缓冲(≈5000行) + rAF 批量渲染
```

分层决策：

1. **泵内攒批**：pump 本地攒行，按 256KiB / 50ms flush。落盘从每行 3 次
   系统调用降到每批 1 次（10MB/s 下 15 万次/秒 → 数百次/秒）；环形缓冲
   每批一次加锁（`push_batch`），tail 语义不变。这是磁盘路径与锁竞争
   的共同解。**对管道读的影响**：读管道仍逐行进行（排空优先），攒的只是
   下游处理；批大小有上界 ⇒ 文件写/轮转让泵停读的窗口有上界（页缓存写
   为毫秒级）——现状逐行写每行都阻塞泵，批化严格缩小了子进程被反压的
   概率窗口（见 D6）。
2. **订阅通道有界化**：`Ring::subscribe` 从无界 `mpsc::channel` 改为
   `sync_channel(K)`，投递用 `try_send`；满则该订阅者丢弃该批并在其
   dropped 计数上累加，下次成功投递时先补发一个 Gap 项。投递单元是
   批（`enum Item { Lines(String), Gap(u64) }`）。环形缓冲与文件不因
   订阅者慢而丢任何东西——它们只收 `push_batch`。
3. **WS 帧批量化**：订阅任务 drain 到即发帧也没必要——按 ≥64KiB 或
   100ms 攒成一帧（现有 LOG 帧格式本就允许一帧多行原始文本，无需改
   格式）；Gap 用**新帧型 `LOG_GAP`(6)**：载荷 = 程序名(u16 len) + 流
   字节 + u64 丢弃行数（定长二进制头，不与内容混载，满足 webui-api 规
   范的"独立帧型"要求）。
4. **out_tx 背压**：会话写出通道已有界（128 帧）；批量化后仍满说明网络
   端真饱和——`send` 带 250ms 超时，超时即关闭该会话（客户端指数退避
   重连，重连即重新拿 tail 快照，自愈）。不做帧级丢弃：那时 gap 会计
   已无意义。
5. **浏览器端**：每流视图保留最近 ≈5000 行（或 2MiB）环形文本缓冲；
   渲染走 rAF 合并（日志流限 ~10fps 追加一次 DOM，一次 textContent 追
   加）；跟随仅当视口贴底；Gap 标记渲染为独立样式行。10MB/s 解码压力：
   压缩帧用浏览器原生 `DecompressionStream('deflate')`，结构化帧用
   `@msgpack/msgpack`（纯 TS、可摇树，约 10KB——这是本变更唯一新增
   前端依赖，手写 msgpack 解码器易错不值）。

**为何不做**：降采样模式（默认行为不应悄悄丢内容语义）、独立日志通道/
SSE（`/ws` 复用已够，瓶颈在逐行而非通道）、无界缓冲保无损（用户已选
丢行+标记）。

### D5. 前端结构：Lit 组件树 + 轻量 store + WS 客户端模块

```
app-shell（已有）
├── 侧栏树: app → 程序（状态徽章组件已有 status-badge）
├── 守护概况条: 版本/monitor_interval/uptime + 系统 CPU/内存 + 刷新频率选择
├── App 概况视图: 程序汇总表（状态/重启/uptime/CPU/内存/日志速率）
└── 程序详情视图: 运行信息 + 控制按钮(确认弹层) + 日志查看器组件
store: 自写小型状态模块（快照+增量合并）+ Lit reactive controller 绑定
ws-client: 连接/重连(指数退避)/解码(msgpack+zlib)/订阅管理/降级轮询
```

- store 用自写模块而非状态库：规模不支撑引入 zustand/redux，现有测试
  基建（vitest + happy-dom）直接可测。
- WS 断开 → 降级轮询 `/api/overview`（按所选刷新频率），顶部横幅提示；
  恢复自动回推送（既有规范行为）。
- 刷新频率/速率窗口/主题类偏好统一 localStorage。

## D6. 零干扰边界：新增路径对受管进程的影响必须为零

线上事故的首要传导链是**管道反压**：子进程的 stdout/stderr 写的是 OS
管道（Linux 默认仅 64KB），泵线程任何原因停读 → 管道满 → 子进程
`write()` 阻塞 → app 被守护工具本身拖慢。逐项审查每个可能让泵停读或
触碰子进程的环节：

```
子进程 ──write──> OS 管道(≈64KB) ──> 泵线程 ──> ┌ 落盘+轮转
                              排空必须永不停止    ├ ring.push_batch (短临界区)
                                                 ├ 订阅投递 (try_send, 非阻塞)
                                                 └ 速率计数 (原子自增)
```

| # | 环节 | 约束 | 落点 |
|---|---|---|---|
| 1 | 文件写/轮转 | 批大小有上界 ⇒ 阻塞窗口有上界；写失败降级仅内存继续排空，绝不重试阻塞 | D4-1 |
| 2 | ring 锁 | `push_batch` 临界区 ≤ 一批（≤256KiB 拷贝，微秒级）；tail 读侧短持锁 | D4-1 |
| 3 | 订阅投递 | `sync_channel` + `try_send`：慢订阅者只丢自己的投递并计数，泵永不等待任何查看者 | D4-2 |
| 4 | 指标采集 | 只读接口（/proc、查询级句柄），无信号/无挂起/无子进程派生；与泵路径无交集 | D1 |
| 5 | 线程故障隔离 | 指标线程 panic → 只丢指标；WS/HTTP 任务 panic → tokio 任务边界隔离，只断该连接；守护循环与泵线程独立，互不波及 | D1/D5 |
| 6 | 守护进程内存 | ring（配置上限）+ 攒批（256KiB）+ 订阅通道（K 批）+ Gap 计数（u64）全部有界 ⇒ 任意速率/总量下 RSS 有界 | D4 |
| 7 | 守护进程 CPU | 1Hz 采样 + 批量化后每秒数百次系统调用，量级可忽略；webui 仅 2 个 tokio worker，且不在守护循环线程上 | D1/D5 |

规范落点：log-management 新增「输出排空零反压」需求（#1/#3/#6 与磁盘
降级）；metrics 新增「采样零干扰」需求（#4/#5）；webui-api 背压需求补
「投递非阻塞、慢消费不反压泵」（#3）。

验证口径（进入 tasks）：压测时断言 (a) 子进程吞吐不因订阅者存在/挂起而
下降，(b) 守护进程 RSS 稳定不随总输出量增长，(c) 磁盘写失败时子进程
不阻塞，(d) 杀掉指标线程守护不受影响。

## Risks / Trade-offs

- [文件系统抖动（慢盘/轮转 rename 卡顿）期间泵停读管道 → 子进程短暂阻塞]
  → 批大小上界使单次阻塞窗口有界；写失败路径降级仅内存；这是与现状
  （逐行写、每行都可能阻塞）相比的严格改善，压测任务断言子进程吞吐
  不回退。
- [10MB/s 下浏览器主线程解码/渲染卡顿] → 解码按帧分摊到 rAF 空闲片；
  仍卡则把 ws 解码挪 Worker（结构已隔离在 ws-client 模块，未来可替）。
- [泵攒批改变时序：极端情况下 flush 延迟 50ms 才落盘] → 崩溃窗口加大
  ≤50ms 的日志丢失可能（原本逐行也只是缓冲写，非 fsync）；环形缓冲同批
  可见，UI 感知无差。
- [`sync_channel` 满时 pump 侧 try_send 开销] → 只在投递分支，热路径
  无锁；K 取足够大（如 64 批 ≈ 16MiB in flight / 订阅者）使正常客户端
  永不触发。
- [Windows 上 OpenProcess 被拒（权限/受保护进程）] → 指标置 null，守护
  日志 warn 一次，不影响其余程序。
- [`/proc` 解析边界（comm 含括号）] → 从最后一个 `)` 右侧解析，单测覆盖。
- [投影字段变多导致快照变大] → MessagePack + 既有 512B 压缩阈值；10
  程序量级实测守住 webui-api 规范的 ≤90% JSON 体积要求即可。
- [刷新节流与 WS 推送节奏不一致造成"切到 1s 却感觉不新鲜"] → 1Hz 采样
  是数据上限；文档/UI 提示明确"1s 档=采样粒度"。

## Migration Plan

纯增量：投影新字段全部 Option/新子结构，旧消费者忽略即可；无配置迁移、
无磁盘格式变化；前端 dist 重建后 `cargo build` 重嵌入。回滚 = revert
整个变更，无残留状态。

## Open Questions

- 批量常量（256KiB/50ms、64KiB/100ms、通道容量 64 批、浏览器 5000 行）
  为初始值，实施时以 10MB/s 压测微调，不影响契约。
- 日志速率窗口 UI 缺省 10s（更平稳），如需改 1s 只是前端默认值调整。
